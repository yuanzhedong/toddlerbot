System Identification

Making the simulator honest — the "match the sim to the robot" knob

One-line idea: system identification (sysID) tunes the simulator's physics until its motors move like the real robot's motors. You don't touch the robot and you don't retrain the policy — you make the sim tell the truth, so a policy trained in it transfers.

Why it matters

When a policy walks in sim but not on the robot, the #1 culprit is the actuator model — the sim's motors are stronger, faster, or less laggy than the real ones. sysID fixes that bias in the simulator. It's the counterpart to domain randomization (which fixes variance by making the policy robust). You usually need both — see the two-knobs cheat sheet.

How it works in this repo

ToddlerBot ships the whole pipeline: a data-collection policy (policies/sysID.py) and an optimizer (tools/run_sysID.py) built on Optuna.

You do NOT hang or use the whole robot. sysID runs on a small single-motor bench fixture — one motor turning a weighted load arm — and you characterize one motor type at a time. It's a one-time job done when you get a new motor (ToddlerBot already ships fitted models for its own motors), not something you repeat per robot or run live on the assembled humanoid.

1 · Build the rig & collect data (chirp sweeps)

Set up the bench fixture (the "sysID section" in the bill of materials) with one motor at ID 0 / 2M baud and the load arm free to rotate. The policy sends a chirp signal — a sine wave that sweeps from low to high frequency, at several amplitudes and gains — and records commanded vs. actual motion. That reveals how the motor really behaves: its lag, damping, friction, torque and speed limits. Run it per motor series (sysID_XC430, sysID_2XC430, sysID_XC330, sysID_2XL430, sysID_XM430):

python toddlerbot/policies/run_policy.py --policy sysID_fixed --sim real --robot sysID_XC430

This saves a timestamped data directory (e.g. 20250301_155535) that the optimizer reads next.

2 · Optimize the model to match (Optuna search)

run_sysID.py searches the sim's motor-model parameters and keeps the set that makes the sim's joint tracking line up with the recorded real data. It uses a TPE (or CMA-ES) sampler and runs many trials. Point --time-str at the data directory from step 1:

python toddlerbot/tools/run_sysID.py --robot sysID_XC430 --time-str 20250301_155535

Watch it converge live in the Optuna dashboard (backed by PostgreSQL — setup is in the repo's sysID docs):

optuna-dashboard postgresql://optuna_user:password@localhost/optuna_db

Think of Optuna as trying hundreds of "what if the motor were a bit weaker / stiffer / laggier?" combinations and keeping the best. No gradients, no policy — just fitting the physics.

3 · Verify, then bake in

The tool plots sim-vs-real joint tracking in both the time and frequency domain — the two curves should now overlap (the "after" panel above). The fitted parameters go into the model for every motor of that type on the robot. From then on the whole humanoid's sim uses honest motors — no per-robot repeat.

Do I need to run sysID?

Usually no. sysID characterizes a motor type, once — not each robot. If your robot uses the standard Dynamixel types (XC330, XC430, 2XC430, XM430, 2XL430), the fitted models already ship in the repo at toddlerbot/descriptions/sysID_<TYPE>/config_dynamics.json and are baked into the assembled model. Reuse them.
SituationRun sysID?
Same robot design / same motor typesNo — reuse the shipped config_dynamics.json.
Another robot, but same motor typesNo — the motor model is shared across units of that type.
A new motor type not in the listYes — characterize it once on the bench rig.
Heavily changed hardware (different gearbox, worn motors, firmware that changes dynamics)Optional — re-run to refresh the model.
But two robots of the same type do differ — just not in a way sysID fixes. Those per-unit differences are handled elsewhere:
  • sysID — per motor type (shared, pre-done).
  • Zero-calibration (calibrate_zero.py, ~1 min) — per robot, for assembly/mounting offsets.
  • Domain randomization — training already randomizes motor gains, mass, and friction, so the policy tolerates the unit-to-unit spread.

What sysID actually tunes

These are the motor-model parameters run_sysID.py searches over (in plain English):

ParameterWhat it controls
dampingResistance that grows with joint speed — viscous friction. Too low in sim → the sim joint coasts more than the real one.
armatureThe motor's own spinning inertia (reflected rotor inertia) — how hard it is to accelerate the joint even with no load.
frictionlossConstant (dry/Coulomb) friction — a fixed amount of torque needed just to start moving.
tau_maxMaximum torque the motor can produce — its strength ceiling.
q_dot_tau_maxThe joint speed at which available torque starts dropping off (the knee of the torque-speed curve).
q_dot_maxThe motor's top (no-load) speed — how fast the joint can move when unloaded.

Together these define the motor's torque-speed curve and how it lags and settles — exactly the things a cheap servo gets "wrong" relative to an idealized sim.

Using it in class

This is advanced / optional and, importantly, it's bench work done ahead of time — not a live activity on the standing robot in Session 3. ToddlerBot already ships fitted motor models, so treat sysID as a concept + instructor demo. When a group's overlay in the lab sheet shows "real motors lag the command," use it as the sysID teaching moment: show a before/after tracking plot from the fixture and the punchline — we didn't change the robot or the policy, we made the simulator honest, once, on the bench.
Gotchas: the fixture needs one motor on ID 0 at 2M baud with the load arm free to swing −90° to +90°; the chirp is fast, so mount it securely and keep hands clear; and motors vary unit-to-unit, so a fitted model is a strong type-level baseline, not a per-unit calibration (that's what zero-calibration on the real robot is for).

The big picture

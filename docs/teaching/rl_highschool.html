Teaching Reinforcement Learning with ToddlerBot

A high-school curriculum built on a real open-source humanoid robot

Audience: intro-CS Python Compute: 2× RTX 3080 (groups) + RTX 6000 Blackwell (instructor) Three 3-hour sessions (3rd needs robots)
Recommendation: two 3-hour sessions. With a dedicated GPU per group and intro-CS Python, students can actually train something themselves — but that payoff only lands if they build RL intuition first (Session 1) and then run and iterate on training (Session 2). A single session forces you to cut either the concepts or the hands-on training, and the big "aha" here is watching a reward curve climb while a robot learns to walk.
Reality check that shapes everything: the repo's default walk training is 1 billion timesteps × 4096 envs (walk.gin, ppo_config.py) — that's hours even on a strong GPU, too long to converge live. So the design splits the work across your two GPU tiers: groups iterate fast on the RTX 3080s with a scaled-down config (reward curve visibly climbs in ~10–15 min), while the RTX 6000 Blackwells produce the pre-trained "gold" checkpoints and run any fuller/longer experiments on demand. Don't try to converge the full run live on a 3080.

What students will be able to do by the end

  • Explain the reinforcement-learning loop (agent, environment, state, action, reward) in their own words and point to each piece in a real robot.
  • Describe what a neural network is and how the robot's "brain" turns sensor numbers into motor commands.
  • Read a reward function, predict the behavior it will produce, and change it to change the robot.
  • Launch a real training run, read a reward curve, and compare experiments.
  • Explain the sim-to-real gap and why domain randomization helps a sim-trained policy work on hardware.
  • Recognize reward hacking — how an agent optimizes what you literally said, not what you meant.

Where this fits: AI → ML → DL → RL → Robot learning

Students often blur these words together. Untangle them once, early, and refer back to this ladder all class. Each row is a special case of the one above it.

The one-sentence version: ToddlerBot uses deep reinforcement learning — a neural network (deep learning) that learns to walk by trial and error (RL), trained in a physics simulator and then moved onto a real robot (robotics + sim-to-real).

The robot's brain: a deep neural network

The "policy" in the table above is a neural network. This is the deep-learning core of the class — worth 20–30 minutes on its own. Keep it concrete: in this repo the brain is literally a function that turns 84 numbers into 12 numbers.

  • Inputs (84): joint angles & speeds, how tilted the torso is, how fast it's spinning, the walk command, and where it is in the step cycle.
  • Hidden layers: three layers of artificial neurons (policy_hidden_layer_sizes = (512, 256, 128) in ppo_config.py). Each neuron computes a weighted sum of the previous layer and passes it through a simple nonlinear function (ELU).
  • Outputs (12): a target position for each of the 12 leg motors, 50 times per second.
  • Weights: every connection has a number (a "weight"). There are hundreds of thousands of them — these are what training changes. At the start they're random, so the robot flails.
How does it learn? Gradient descent. After each batch of trials, the trainer nudges every weight a tiny bit in the direction that would have earned more reward (learning rate 3e-5). Repeat millions of times. No one tells it the "right" joint angles — it discovers them. This is the same math behind image and language models; here the "grade" is reward instead of a labeled answer.
Two networks: the student and the tutor (actor-critic). PPO actually trains two nets. The policy (actor) decides actions from the 84 things the real robot can sense. A second value network (critic) reads 151 numbers — including things only the simulator knows, like true body velocity and foot contact forces — and estimates "how good is this situation?" The critic coaches the actor during training, like a tutor with the answer key during study, then is thrown away at deployment. The robot walks using the policy alone. This is a great "aha" for students: the robot is trained with more information than it's allowed to use when it performs.

Session 1 — "Meet the robot and the RL loop"

Goal: build RL intuition and get hands in the simulator. No training yet.

Hour 1

RL intuition, no code (whiteboard + discussion)

  • Trial-and-error learning: pets, video games, learning to ride a bike. What's the "reward"?
  • Introduce the loop diagram above. Contrast with "just program the walk" — why that's brittle for a humanoid.
  • Interactive: "You're the reward designer. A robot should walk forward. What do you reward? What goes wrong?" Their naive ideas (reward forward speed only → robot dives/faceplants) are exactly what real reward shaping wrestles with.
Hour 2

The brain + hands in the sim (on the group machines)

  • First ~20 min: "the robot's brain" (the deep-learning section above). Draw the 84→12 network on the board; have students name a few of the 84 inputs and the 12 outputs. Land the idea that training just tunes the weights.
  • On each group's 3080 machine (repo pre-installed), run a motion replay so they see the robot immediately:
python toddlerbot/policies/run_policy.py --policy replay --path motion/push_up_2xc.lz4
  • Load a pre-trained walk policy and watch it walk. Then perturb it live: change the walk command (speed/turn), add a push. Robustness = "it learned to recover," not scripted.
  • Have them narrate the loop diagram against what they see on screen — where are the 84 inputs coming from? Where do the 12 outputs go?
Hour 3

Read the reward, form hypotheses

  • Open walk_env.py together; walk through 4–5 reward terms in plain English.
  • Group worksheet: for each term, "what behavior does this encourage / what breaks if you delete it?" Each group commits to a hypothesis to test next session (e.g. "remove the upright/roll reward → it walks tilted or falls").
  • Optional (if there's a gap before Session 2): kick off one scaled-down training run to leave going, so Session 2 opens with a finished curve to look at.

Session 2 — "Shape the reward, train the robot"

Goal: understand PPO at a high level, then run and compare real training experiments.

Hour 1

How PPO learns + launch a baseline run

  • PPO at high-school altitude: try actions, keep what earned reward, 4096 robots exploring at once. No derivations — use the "4096 toddlers learning to walk simultaneously" image.
  • Each group launches the scaled-down baseline training on its 3080 and watches the reward curve climb in real time in Weights & Biases (the repo already logs to wandb).
Hour 2

The reward-shaping experiment (the core project)

  • Each group edits the config to test their Session-1 hypothesis: zero out or change a reward weight, or change the target walk speed. One-line edits in the gin/config.
  • They launch a short run on their 3080 and compare their curve + behavior video against the baseline and the pre-trained "gold" policy.
  • This is where the learning happens: "we removed the foot-slip penalty and it learned to skate."
  • Hand-off: if a group's experiment looks promising, kick the same config off on an RTX 6000 Blackwell for a longer run so they can see the converged payoff in the next break or by wrap-up.
Hour 3

Sim-to-real, present, and wrap

  • Sim-to-real demo (~25 min): re-train or reload with pushes turned on (DomainRandConfig.add_push = True) and shove the robot in sim — it stays up. Use it to teach the reality gap and domain randomization (full section below). Show the punchline: the same policy file runs in sim (--sim mujoco) or on the real robot (--sim real).
  • Presentations: each group gives a 2-minute show-and-tell — hypothesis, reward curve, video, what actually happened (and any reward hacking they caught).
  • Wrap + tee up Session 3: revisit the AI→ML→DL→RL ladder — they've now touched every rung. The cliffhanger: "your policy walks in sim… but will it walk on the real robot? Next time we find out."

Session 3 — "Sim-to-real: make it walk in the room"

Goal: take a trained policy onto the physical ToddlerBot, measure the sim-to-real gap, and iterate to shrink it. Requires one robot per group.

Safety first — real humanoids, real risk. Robots on a safety stand / harness for first runs, a clear zone around each bench, a known kill switch, and one rule students repeat back: never grab a falling robot — let it fall, hit stop. Brief this before any motor is powered.
Which policy do they deploy? Their 15-minute Session-2 policies usually aren't robust enough for hardware, so each group deploys a provided "gold" checkpoint (trained to convergence on a 6000) as the baseline, and may try their own as a stretch goal. Print the one-page cheat sheet — it's the bench reference for the whole session — and give each group the Session 3 lab sheet to fill in as they go (safety check-off, predict/observe boxes, the diagnose table, before/after comparison). For yourself, run it from the Session 3 run-of-show — a minute-by-minute timeline with a gotcha playbook (robots that won't stand, gold policy still falling, jammed retrain queue).
Hour 1

Safety, calibrate, and first contact with reality

  • Safety briefing (~10 min) — the callout above, demonstrated on one robot.
  • Calibrate & stand (~20 min): zero-calibrate the motors (tools/calibrate_zero.py), then confirm a clean stand: run_policy.py --policy stand --sim real. If it can't stand still, it can't walk — fix this first.
  • Re-test in sim (~10 min): run the exact policy file with --sim mujoco so you know the brain is good before trusting hardware.
  • Predict, then deploy (~20 min): each group writes down what they expect, then runs run_policy.py --policy walk --sim real --record. Reality is almost always imperfect — leaning, drifting, tip-toe, or a fall. Record it; that recording is the data for Hour 2.
Hour 2

Diagnose the gap (this is the science)

  • Overlay sim vs real (~30 min): run tools/sim2real_eval.py on their recording to overlay motor position/velocity/torque and IMU. Groups fill the diagnose table on the cheat sheet — where do the curves split?
  • Classify & hypothesize (~10 min): calibration offset? motor lag? latency? mass/friction? overfit? Each group names the failure and which of the two knobs they'll turn (match the sim, or make the policy robust).
  • Apply the cheapest fix (~20 min): on the standing robot the live knobs are calibration (redeploy immediately, no retrain) and domain randomization (retrain). If the gap points to the actuator model, that's a system-ID issue — a separate bench procedure done ahead of time, not live here (see the sysID page); use it as a teaching moment, and rely on a pre-fitted model. Hand-off: any fix needing a full retrain goes to the instructor's 6000s while the group keeps analyzing.
Hour 3

Close the loop, demo, reflect

  • Redeploy with the fix (~25 min): run again, record, and overlay before vs after in sim2real_eval.py. Did the gap shrink? Groups whose fix needed a retrain deploy the 6000-retrained variant.
  • Iterate once more if time allows — the loop is the lesson.
  • Demos (~15 min): each group shows a before/after video + overlay, states which knob they turned and why, and what's still off.
  • Wrap (~10 min): the two-knobs mental model, "this loop is the research," and the honest truth that nobody nails transfer on the first try. Tease the frontier: push-recovery and multi-skill locomotion.
Session 3 deliverables per group: a before/after real-robot video, a filled diagnose table, and one sentence — "we turned this knob because the overlay showed that." Success = the robot takes real steps and the group can point to the gap they closed (not necessarily a perfect walk).

Sim-to-real: crossing the reality gap

This is the idea that makes robot learning special, and students find it genuinely surprising. Budget real time for it in Session 2.

Why train in a simulator at all?

  • Speed & scale: the sim runs 4096 robots in parallel, faster than real time. The full walk sees ~1 billion timesteps — that's centuries of real-world practice, done in hours.
  • Safety & cost: a falling sim robot costs nothing. A real one breaks. Early policies fall constantly.
  • Perfect information: in sim you know everything (true velocity, contact forces) — which is how the critic network can coach the policy.

The catch: the reality gap

A simulator is not reality. Real friction, motor delays, sensor noise, and slightly-wrong masses all differ from the sim. A policy that gets too good at the sim's exact quirks — a form of overfitting — can walk beautifully on screen and fall over on the real robot. That failure is the sim-to-real gap.

The fix: domain randomization

Instead of one perfect simulator, train across thousands of slightly different, randomized ones. Each episode, the sim rolls new physics. To survive all of them, the policy has to learn a robust, general walk — and then the real world just looks like "one more variation it already handles." These are the actual quantities ToddlerBot randomizes (DomainRandConfig in mjx_config.py):

What's randomizedWhy it matters for the real robot
Ground friction (0.4–1.0×)Real floors are more or less slippery than the default.
Body mass (±20%)The CAD model never matches the built robot exactly.
Motor strength & gains (kp/kd, torque ±10%)Real motors vary unit-to-unit and heat up over time.
Control delay & gear backlashReal commands arrive late and joints have a little slop.
Random shoves (a push every ~2 s)Teaches active balance recovery — the visible "wow" demo.
Starting tilt of the torsoThe robot won't always start perfectly upright.

Class activity: flip add_push = True and shove the robot in the viewer. Then ask: "why would practicing with random shoves in sim help it handle being bumped in real life?" That's domain randomization in one sentence.

From sim to the physical ToddlerBot

The same trained network runs in both worlds — only where the 84 input numbers come from changes:

Point students at run_policy.py: the --sim mujoco vs --sim real flag is the whole handoff. On real hardware the 84-number observation is assembled from the robot's IMU and joint encoders instead of the simulator, and the 12 outputs drive actual motors 50 times a second.

After training: deploying and iterating

Training produces a policy file — getting it to walk on the real robot is a second project, and it's where most real work happens. This is advanced material: use it for the Session 2 wrap, an extension day, or your own reference.

From a finished run to the robot

  1. Training's output: train_mjx.py saves your run to results/<run_name>/ and exports the policy to model_best.onnx (also uploaded to W&B). That small ONNX file is the deployable brain — the 84→12 network, frozen.
  2. Re-test the ONNX in sim first. Export bugs (observation order, scaling) are common. Run the exported file in MuJoCo before touching hardware: 
    python toddlerbot/policies/run_policy.py --policy walk --sim mujoco --vis view
    If it misbehaves here, the bug is in export, not sim-to-real.
  3. Prep the hardware: zero-calibrate the motors (tools/calibrate_zero.py — a few degrees of ankle/hip offset will topple a walk), confirm a clean stand (--policy stand --sim real), and use the safety stand for first runs.
  4. Deploy and record: 
    python toddlerbot/policies/run_policy.py --policy walk --sim real --record
    Now the 84 inputs come from the IMU + encoders and the 12 outputs drive real motors at ~50 Hz. --record logs the rollout so you can measure the gap.

"It walks in sim but not on the robot" — the iteration loop

This is the sim-to-real gap in practice. The golden rule: measure the gap before changing anything. The repo gives you a principled loop, not guesswork.

Diagnose first: what does the gap look like?

Record a real rollout and overlay it against sim with tools/sim2real_eval.py (it plots motor position, velocity, torque, and IMU, sim vs real). Where the curves split tells you the cause — and the cheapest fix:

What you see in the overlayLikely causeFix (cheapest first)
Constant offset; robot leans one wayMotor zero / calibration offcalibrate_zero.py — no retrain
Real motors lag or undershoot the commandActuator model too strong/fast in simSystem ID — bench procedure, done ahead of time (below)
Right shape, shifted in timeLatency mismatchtune n_steps_delay
Tips over under load / when movingMass / friction / inertia wrongmeasure (test_mass.py), fix MJCF, or widen DR
Every metric matches but it's still unstablePolicy overfit to sim quirkswiden domain randomization + retrain

The two fixes: system ID and domain randomization

  • Make the sim match the robot (fixes bias): tools/run_sysID.py uses Optuna to fit the sim's motor dynamics (torque/speed limits, damping, friction) to real data collected on a single-motor bench fixture (per motor type, once). Re-run sim2real_eval.py to confirm the sim now tracks reality. No policy retrain needed — you're making the simulator honest. Full walkthrough on the system-identification page.
  • Make the policy not care (fixes variance): widen the ranges in DomainRandConfig around your identified values and turn on perturbations, then retrain on a 6000: 
    DomainRandConfig.add_push = True          # learn to recover from shoves
DomainRandConfig.friction_range = [0.3, 1.1]
DomainRandConfig.kp_range = [0.8, 1.2]    # motor-gain spread
The mental model to teach: there are two knobs, and students should always name which one they're turning — make the sim match the robot (system ID, calibration, better model) or make the policy robust to being wrong (domain randomization). You almost always need both. Honest note for the class: this loop is the actual research — making cheap-robot transfer reliable is a big part of what the ToddlerBot papers contribute.

Instructor prep checklist

Budget a few hours before the first session.

  1. Pre-train 1–2 checkpoints on the RTX 6000 Blackwells (a good walk, maybe one "broken reward" example) to demo — these are your reliable ground truth. With 4 cards you can train several skills/variants in parallel.
  2. Class config (ready to use): walk_class.gin scales the run down (~30M timesteps, 2048 envs) so it shows clear improvement in ~10–15 min. Layer it on top of walk: 
    python toddlerbot/locomotion/train_mjx.py --env walk --gin-file "walk walk_class"
    Time it on a 3080 first; the 10 GB of VRAM should hold 2048 envs, but drop num_envs to 1024 if you hit out-of-memory.
  3. Prep the two 3080 group machines: repo installed, checkpoints downloaded, W&B logged in, and a one-line launch script for replay / load-policy / train. Hide the messy setup so students spend time on concepts, not pip. (No cloud needed — everything runs locally.)
  4. Reward worksheet (ready to use): rl_reward_worksheet.html — the 10 active reward terms with blanks for "what it encourages / what breaks at 0," a prediction section, the exact run commands, and a collapsible instructor answer key. Print-friendly.
  5. Seed hypotheses so no group is stuck at a blank page.
  6. Session 3 (hardware) prep: each robot charged, zero-calibrated, and pre-loaded with a gold walk checkpoint; safety stands/harnesses and a kill switch per bench; the sysID sweep + run_sysID.py pipeline tested end-to-end beforehand; a retrain queue on the 6000s ready for hand-offs; the cheat sheet + lab sheet printed for every group; and your own run-of-show (minute-by-minute + gotcha playbook) to hand.

If you have more time (extensions)

  • Try a different skill: the repo ships gin files for crawl, get_up, cartwheel, stairs, and more — same command, different --env. Great for "what reward would you write for a cartwheel?"
  • Harder world: switch on rough terrain or stairs (TerrainConfig) and watch a flat-ground policy struggle, then retrain.
  • Speed limits: widen or narrow the command range and see how fast it can learn to walk before it falls.
  • Converged payoff: run a group's best experiment to (near) convergence on an RTX 6000 Blackwell and compare the video to their 15-minute version.
  • Real deployment (if you have a physical ToddlerBot): take a policy the students trained and run it with --sim real. Nothing beats seeing their reward function walk in the room.

Key terms (glossary)

TermPlain-English meaning
AgentThe learner/decision-maker. Here: the policy network.
EnvironmentThe world the agent acts in. Here: the MuJoCo physics sim.
State / ObservationWhat the agent knows right now — the 84 sensor numbers.
ActionWhat the agent does — the 12 motor targets.
RewardA number scoring how good the last action was. The agent tries to maximize the total over time.
PolicyThe agent's strategy — the neural network mapping observations to actions.
EpisodeOne attempt, from start until the robot falls or time runs out (up to 1000 steps).
Neural networkA stack of layers of simple "neurons" with tunable weights that together compute a complex function.
WeightsThe numbers inside the network that training adjusts. Learning = finding good weights.
Gradient descentThe method for improving weights: nudge each one in the direction that increases reward.
PPOProximal Policy Optimization — the specific RL algorithm used here to update the policy safely.
Actor-criticTraining with two networks: an actor (the policy) and a critic that estimates how good states are.
Domain randomizationRandomizing sim physics each episode so the policy generalizes to the real world.
Sim-to-real gapThe performance drop when a sim-trained policy meets messy reality.
Reward hackingWhen an agent maximizes the literal reward in an unintended way.
OverfittingGetting too specialized to the training conditions and failing on new ones.
